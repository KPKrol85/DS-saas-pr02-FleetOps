### Changed

- Tied the production service-worker precache to the runtime assets the Vite build actually emits, closing `O-02`: a public route that was precached but never visited now renders styled and interactive on a first offline navigation instead of loading only its cached HTML. Vite content hashing stays enabled and no generated filename is maintained by hand — a new repository-owned Rollup plugin in `vite.config.js`, `fleetopsServiceWorkerPrecache()`, runs on build only, in `generateBundle` with `order: "post"`, reads the emitted markup of each precached document, collects its `<link rel="stylesheet">`, `<link rel="modulepreload">` and `<script src>` URLs, and keeps the ones matching a `.css`/`.js` file the same bundle emitted. Dependent generated chunks are therefore included exactly when the real Vite output graph requires them, while icons, fonts, images, screenshots, the manifest and other `public/` passthroughs stay out: this is an initial offline availability guarantee, not full offline mirroring, and normal asset requests keep the existing stale-while-revalidate strategy. `404.html` is excluded as the online host error document, `offline.html` as self-contained `O-01` infrastructure. `public/sw.js` remains the single maintained worker source and gained one placeholder, `RUNTIME_ASSET_URLS`, which the plugin replaces when it emits `dist/sw.js`; the generated worker is a pure build artifact, the derived list is deduplicated and sorted so equivalent builds are byte-identical, and the build fails loudly if a precached document, the placeholder or any runtime asset is missing. Because the URLs come from the build that emitted the files, `cache.addAll()` cannot fail on a stale asset, and the install/activate lifecycle is otherwise unchanged. The cache version advanced from `fleetops-v1.11` to `fleetops-v1.12` and activation still removes every older `fleetops-` cache. No Workbox, `vite-plugin-pwa` or other dependency was introduced, the worker architecture was not redesigned, and the development server is unaffected: the plugin never runs outside a build and the worker is still registered in production only. `OFFLINE_FALLBACK_URL` semantics, public-route classification, requested-document lookup, network-first navigation, fulfilled-response passthrough, `Response.error()` behaviour, cache-key normalization and unknown-route handling are unchanged; `offline.html` gains no dependency on the precached assets. ### Fixed

- Fixed collapsed accordion panels staying `hidden === false` whenever a collapse produced no `max-height` transition. `scripts/ui/components/accordion.js` applied `hidden` only from a `transitionend` listener, but that event is not guaranteed: when a panel is collapsed again before the browser has rendered a frame at the opened `max-height`, the computed value goes from `0px` to `0px`, no transition is created in either direction and no transition event of any kind is dispatched, so the panel ended visually collapsed with `aria-expanded="false"` while remaining exposed to assistive technology — `aria-expanded` and `hidden` described different states. Semantic completion no longer depends on the transition alone: `transitionend` stays the fast path and a fallback derived from the panel's own computed `transition-duration` and `transition-delay` guarantees the collapse finishes, so the fallback is tied to real transition timing rather than a fixed delay. The completion callback is idempotent — it removes its listener and clears its timer before acting — and re-checks that the panel is still collapsed, so a stale collapse can no longer hide a panel that has been reopened in the meantime; every state change cancels the pending completion first, leaving no callback able to mutate a later state. `transitioncancel` is deliberately not treated as completion, because a collapse that interrupts an in-flight open cancels that open transition and finishing there would cut the closing animation short; a cancelled transition is covered by the timer instead. The immediate initial collapse (`hidden` applied synchronously by `Accordion.init`) and the reduced-motion path (zero effective duration completes at once) are unchanged, as are the markup contract, the ARIA relationships, `aria-controls` id generation, the keyboard and button semantics and the open/close animation. No CSS and no test changed: the defect was exposed by the existing accessibility test during the PH8-03 smoke run, which now passes in full-suite context. This also closed the PH8-03 verification, run against the corrected implementation: `npm run qa:css-vars` exit 0 (971 `var()` usages, 77 custom property definitions, 11 source CSS files), the complete Playwright smoke suite exit 0 with 26 of 26 tests passing, and `npm run build` exit 0 on Vite 7.3.6 with 38 modules transformed and a complete `dist/` artifact.
- Fixed the service worker converting fulfilled HTTP responses into network failures during navigation. `networkFirstNavigation` in `public/sw.js` threw whenever `!response.ok`, so any non-2xx navigation response was discarded and pushed into the offline cache fallback; for an unknown URL online this meant the host's valid HTTP 404 was replaced by `Response.error()` and controlled clients saw a browser network-error page instead of the error document. The synthetic throw was removed: a fulfilled `fetch()` now returns its response to the browser unchanged whatever the status, and only a rejected `fetch()` falls back to `matchNavigationCache()`, with `Response.error()` still returned on a cache miss after a real network failure. The fix is generic rather than 404-specific, so redirect and 5xx responses also stop being routed into offline recovery. The cache-write policy is untouched — `cacheNavigationResponse()` still stores only successful responses for known public routes, so a fulfilled non-2xx response is returned but never cached and unknown URLs are never replaced with the application shell — as are `matchNavigationCache()`, `staleWhileRevalidate()`, the install and activate lifecycle and cache-key normalization. `CACHE_NAME` stays `fleetops-v1.10` and `PRECACHE_URLS` is unchanged, since no cached content or key changed, and `404.html` was not precached: being offline does not prove a URL does not exist. Covered by one focused Playwright test in the existing real-service-worker scope, which asserts that a navigation to `/missing-page` under service-worker control completes with HTTP status 404 instead of failing. Netlify's custom `404.html` body and the trailing-slash redirects remain deployment-only verification, because the Vite preview serves a plain 404 and does not process `_redirects`.
- Fixed unknown URLs being served the landing document with HTTP 200 instead of reaching the maintained error page. `public/_redirects` ended with `/* /index.html 200`, an SPA history fallback the project does not need: every public route is a real directory document built as its own Vite entry (`appType: "mpa"`), and the demo application lives entirely in the hash, which is never sent to the server. That final rule was removed and not replaced — no second catch-all and no explicit `/* /404.html 404`, so unmatched paths fall through to the platform's normal custom-404 handling of the deployed root `404.html`. The `/assets/*` passthrough and the ten trailing-slash 301 redirects are unchanged, as is the hash router. `404.html` also stopped depending on request depth: its four icon links, its manifest link and its home button moved from `./assets/favicon/...` and `href="./"` to `/assets/favicon/...` and `href="/"`, with the visible text, styling, font preload, stylesheet link and SEO metadata untouched. The HTTP status actually returned for an unmatched path can only be confirmed against a deployed environment.

### Added

- Added a branded FleetOps offline fallback document for navigations that genuinely fail. `offline.html` is a new maintained Vite build entry emitted as `dist/offline.html`, and `public/sw.js` precaches it under an explicit `OFFLINE_FALLBACK_URL` that is deliberately kept out of `PUBLIC_ROUTE_URLS`, because it is PWA infrastructure rather than a public route. After a rejected navigation request the service worker still prefers the cached copy of the document actually requested; only when that is missing does it answer the original request with the precached offline page, and it does so without redirecting, so the requested URL stays in the address bar and the browser's own connectivity error page remains only the emergency path if even the precached document is unavailable. `CACHE_NAME` advanced from `fleetops-v1.10` to `fleetops-v1.11` because the required precache contents changed, and activation still retires older `fleetops-` caches. Real online HTTP responses are untouched: a fulfilled `fetch()` still reaches the browser unchanged whatever its status, so an unknown URL online still returns the host's real 404 and a server error still returns the real error response — being offline is not evidence that a URL does not exist, and `404.html` remains the online error document rather than the offline fallback. The page communicates connectivity failure only: FleetOps text branding, one `main` landmark, a single `h1` "Brak połączenia z siecią", a concise explanation, one plain anchor back to `/`, `noindex`, and its critical styles inline so it needs no stylesheet, script, font or image and stays readable with no network at all. It does not claim the requested page is missing and does not imply that any change was queued or will be synchronized, so the `PH5-01` rejection of offline mutations is unchanged. Covered by one focused Playwright test in the existing real-service-worker scope, which navigates offline to an uncached path and asserts that the fallback renders while the requested URL is preserved; the existing online-404 test is unchanged.
- Added the standalone FleetOps static frontend implementation, covering public marketing and legal pages (`product`, `features`, `pricing`, `about`, `contact`, `security`, `careers`, `privacy`, `terms`, `cookies`, `404.html`) and a hash-routed demo application under `#/app`, `#/app/orders`, `#/app/fleet`, `#/app/drivers`, `#/app/reports` and `#/app/settings`.

### Testing

- Replaced the obsolete contact-form test ("public contact form discloses that it is a demo and its submit transmits nothing") with two focused tests of the new runtime contract. Both intercept the same-origin `POST /` in Playwright, so no request reaches Netlify and the suite creates no real submissions. The success test asserts the provider metadata in the rendered HTML (form name, method, `data-netlify`, `data-netlify-honeypot`, the hidden `form-name` value, an empty and non-visible honeypot), holds the intercepted response to confirm that the submit control is disabled and reads `Wysyłanie…` while the request is in flight and that no toast exists before the provider answers, and only then verifies the captured request: one `POST`, `application/x-www-form-urlencoded`, and a payload carrying `form-name=fleetops-contact`, the four user fields and an empty `bot-field`. After the simulated success it checks the confirmation, the cleared fields and acknowledgement, and the restored control. The failure test answers the same request with HTTP 500 — the case a `.catch()`-only implementation would report as success — and asserts that the assertive error is exposed, that no success message appears anywhere, that all typed values and the acknowledgement survive, that the control becomes usable again, and that the published e-mail and telephone fallbacks stay visible.
- Added Playwright smoke tests in `tests/smoke.spec.js` covering public pages and demo application routes.
- Added a CSS custom-property consistency check (`scripts/qa/check-css-vars.js`) exposed as the `qa:css-vars` package script.
